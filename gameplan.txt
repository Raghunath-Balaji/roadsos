# Road SOS - Architecture & Implementation Plan

## Background & Motivation
Road SOS is a dual-sided React Native mobile application designed for emergency reporting and response. It empowers citizens to report accidents (either for themselves or others) and enables helpers (ambulances, hospitals) to receive these alerts and navigate to the scene. The app integrates Google OAuth, Firebase for real-time data, and a specialized on-device/edge AI bot for First Aid guidance.

## Scope & Impact
- **Frameworks:** React Native, Expo, Tailwind CSS (NativeWind).
- **Backend:** Firebase (Auth, Firestore for profiles/reports, Realtime DB for live tracking).
- **AI Integration:** Gemma 2B model trained with Unsloth for First Aid guidance.

## Architecture

### 1. User Roles
- **Citizen:** Can self-report, report for others, chat with the First Aid AI, and track incoming help.
- **Helper:** Receives emergency alerts, accepts them, and provides real-time location updates while en route.

### 2. Core Screens & Flow
- **Authentication:** Email and Password via Firebase.
- **Citizen Helperdashboard:** Map view showing current location, and three severity buttons (Green, Yellow, Red) for instant self-reporting.
- **Third-Party Report Screen:** Form to submit location, severity, photograph, and description on behalf of someone else.
- **First Aid Assistant:** Chat interface powered by the First Aid AI model.
- **Live Tracker:** Map view displaying the real-time location of the accepted helper en route.
- **Profile:** Manage personal and medical details used for self-reporting.

### 3. Technical Stack Decisions
- **Routing:** Expo Router for file-based navigation (e.g., `app/(citizen)`, `app/(helper)`, `app/(auth)`).
- **Database:**
  - *Firestore:* User profiles, static emergency reports, and AI chat history.
  - *Realtime Database:* High-frequency, low-latency live tracking of helpers.
- **AI Model Deployment:** Integrating a local Gemma 2B model on mobile requires native modules (e.g., `react-native-llama` or `MLC LLM`). *Note: This requires moving away from standard Expo Go to Custom Development Builds (EAS Build).*

## Implementation Plan

### Phase 1: Setup & Firebase Integration
1. Initialize Firebase project and integrate Firebase JS SDK (or React Native Firebase if native features are needed).
2. Setup Google OAuth login.
3. Configure Expo Router structure for Authentication, Citizen Tabs, and Helper Tabs.

### Phase 2: Citizen Side Development
1. **Profile Setup:** Screen to input and save user/medical details to Firestore.
2. **Helperdashboard:** Implement the map component (`react-native-maps`) and the three severity buttons for self-reporting.
3. **Report Screen:** Form with image picker and description fields to report on behalf of others.

### Phase 3: Helper Side & Real-Time Tracking
1. **Helper Helperdashboard:** Feed of incoming emergency reports with "Accept" functionality.
2. **Live Tracking:** When a helper accepts, publish their location updates to Firebase Realtime DB.
3. **Citizen Tracker:** Read the helper's location from Realtime DB and display it on the Citizen's map.

### Phase 5: Bystander Reports & Enhanced Alert Management
1. **Schema Update:** Enhanced `ActiveAlert` interface in `alertService.ts` to support `isBystanderReport` and `reportedPatientName`.
2. **Bystander Creation Logic:** Implemented `createBystanderAlert` to write directly to `liveAlerts`, bypassing personal user history for bystander reports.
3. **Enhanced Alert Actions:** Updated `acceptAlert` and `markAsSaved` to conditionally skip user history updates based on the report type.
4. **Bystander UI:** Developed `app/(tabs)/report.tsx` with a form requiring mandatory camera capture, optional patient name (defaults to John Doe), severity selection, and optional details.
5. **Helper Dashboard Integration:** Updated `app/(helper)/dashboard.tsx` to conditionally display bystander-specific details and patient names fetched from `userDetails` for standard alerts.

## Verification & Testing
- Test Google OAuth flows for both new and returning users.
- Verify that self-reporting instantly pushes to the helper feed.
- Simulate helper movement to verify real-time tracking latency.
- Ensure the AI model responds accurately to first-aid scenarios.
- Verify bystander reports require a photo and show up correctly on the Helper Dashboard without reporter medical history.

Here is the complete, detailed implementation plan. Because this is an Android-only app, we can leverage Android's Foreground Services and Window Flags to keep the accelerometer
  alive in the background and forcefully wake the screen when a crash happens.

  To keep the codebase clean, we will let Native Android (Kotlin) handle the background sensor math, and let React Native (JS) handle the UI, sound, timer, and Firebase database
  writes.

  ---

  Phase 1: Permissions & System Configuration
  To run in the background and wake the screen, Android requires specific permissions.

  1. app.json
   * What will be altered: We will add necessary Android permissions and specify the background mode.
   * Additions: WAKE_LOCK, FOREGROUND_SERVICE, FOREGROUND_SERVICE_SPECIAL_USE (or LOCATION), USE_FULL_SCREEN_INTENT, VIBRATE.

  2. android/app/src/main/AndroidManifest.xml
   * What will be altered: The core Android manifest file.
   * Additions:
       * Register the new CrashService (our background worker).
       * Add android:showWhenLocked="true" and android:turnScreenOn="true" to your MainActivity so it can bypass the lock screen when a crash is detected.

  Phase 2: The Custom Native Android Module (Kotlin)
  We will write a small native bridge to poll the accelerometer while the app is minimized.

  3. android/app/src/main/java/com/raghunathbalaji/roadsos/CrashService.kt (NEW FILE)
   * What it does: This is the Android Foreground Service. It displays a persistent notification ("RoadSOS Drive Mode Active"). It registers a SensorEventListener for the
     accelerometer.

   * The Trigger: If G-Force > 4.0, it fires an Intent to forcefully launch/wake up MainActivity and sends a Javascript event: CRASH_DETECTED.

  4. android/app/src/main/java/com/raghunathbalaji/roadsos/CrashModule.kt (NEW FILE)

# Plan: Implement Drive Mode with Crash Detection

## Objective
Add a "Drive Mode" feature to the RoadSOS app that tracks real-time accelerometer data to detect sudden surges indicative of a crash. When active, this mode will implement a "soft lock" to prevent accidental exiting via gestures or the back button.

## Prerequisites
1.  **Install `expo-sensors`**: This package is required to access the device's accelerometer.

## Key Files & Context
*   **`package.json`**: Needs to be updated with the `expo-sensors` dependency.
*   **`app/(tabs)/_layout.tsx`** or a global context/provider: To manage the global state of "Drive Mode".
*   **`app/(tabs)/sos.tsx`** (or whichever is the primary citizen screen): To add the UI toggle for "Drive Mode".
*   **New Component: `components/DriveModeOverlay.tsx`**: A full-screen or prominent overlay that appears when Drive Mode is active, handling the "soft lock" and displaying status.
*   **New Service: `services/crashDetection.ts`**: To encapsulate the accelerometer logic and threshold calculations.

## Implementation Steps

### Phase 1: Setup & Service Creation
1.  **Install Dependency**: Run `npx expo install expo-sensors`.
2.  **Create `crashDetection.ts`**:
    *   Import `Accelerometer` from `expo-sensors`.
    *   Set the update interval (e.g., 100ms) for high-frequency tracking.
    *   Implement logic to calculate the total G-force from x, y, and z axes: `Math.sqrt(x*x + y*y + z*z)`.
    *   Define a standard crash threshold (e.g., ~4G).
    *   Create a subscription mechanism to notify the UI when a crash is detected.

### Phase 2: State Management & UI Toggle
1.  **Global State**: Implement a way to track if `isDriveModeActive` is true (using React Context or a simple state lifted to a high enough level).
2.  **Drive Mode Button**: Add a persistent, easily accessible button (e.g., a Floating Action Button or a bottom-right popup as requested) on the main user dashboard (`sos.tsx` or similar) to toggle `isDriveModeActive`.

### Phase 3: Drive Mode Overlay & Soft Lock
1.  **Create `DriveModeOverlay.tsx`**:
    *   This component will render conditionally based on `isDriveModeActive`.
    *   It should cover the screen to prevent interaction with underlying elements.
    *   Implement a visual indicator that Drive Mode is active and monitoring.
    *   Provide a secure way to exit Drive Mode (e.g., a "Slide to Unlock" or "Hold to Exit" button) to prevent accidental closure.
2.  **Implement Soft Lock**:
    *   Use React Native's `BackHandler` to intercept hardware back button presses on Android and prevent the app from minimizing or going back.
    *   If using React Navigation, ensure swipe-to-go-back gestures are disabled for the screen hosting the overlay.

### Phase 4: Integration & Crash Response
1.  **Start/Stop Tracking**: When Drive Mode is activated, start the `Accelerometer` subscription in `crashDetection.ts`. When deactivated, stop it to save battery.
2.  **Handle Crash Event**: When the service detects a surge exceeding the threshold:
    *   Trigger an immediate alert in the UI (e.g., a loud sound or red flashing screen).
    *   Initiate a countdown (e.g., 10 seconds). If the user doesn't cancel it, automatically trigger the SOS flow.

## Verification & Testing
1.  Verify `expo-sensors` installs correctly and the app builds.
2.  Test the "Soft Lock" to ensure the back button and gestures do not close the Drive Mode overlay accidentally.
3.  Simulate a crash by physically moving the device rapidly (safely!) while connected to the debugger to verify the G-force calculation and threshold triggering.
4.  Ensure the Accelerometer stops tracking when Drive Mode is disabled.
